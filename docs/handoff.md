## What v1 had to do

This is the original brief, condensed; the README describes how each point was met. Keep these constraints unless the owner changes them.

- **Platform:** native iPhone app, iOS 17+, Swift, SwiftUI, SwiftData, CoreBluetooth and HealthKit.
- **Apple frameworks only:** no packages, backend, accounts, telemetry, analytics or network calls. It works fully offline, so there's nothing to deploy (no Vercel, no Supabase).
- **Name and bundle ID:** the app is "vitals", lowercase. The bundle ID `dev.gtfol.vitals` is a setting, not final.
- **Design:** dark-first gtfol look. Tabs are train, history and settings.
- **Architecture:** one local SwiftData store, and one session coordinator that ties logging, Bluetooth and HealthKit together.
- **Workout:** strength by default, routines, heart-rate-only activities and an exercise catalog with search. Exercises can be reordered.
- **Sets:** working or warm-up, reps, load, done and completion time. lb or kg, stored in kg. Previous-session values show alongside, a new set copies the one before it, and the rest timer runs from timestamps.
- **Heart rate:** live from the strap, with gaps never filled in, and automatic reconnection.
- **Finish:** finish once, with separate local and Apple Health states. Health export can be retried without duplicates. After a relaunch, an unfinished workout can be continued or finished.
- **History:** sessions with editable detail. Records are heaviest load and Epley estimated 1RM for 1–10 reps. The first session is a baseline, and bodyweight movements are excluded. Exercise history shows past sets and bests.
- **Helio Strap:**
  - Standard Heart Rate Measurement `0x180D`/`0x2A37`, with RR intervals stored raw.
  - Battery from `0x180F`/`0x2A19`.
  - A restore identifier and the `bluetooth-central` background mode.
  - Connects only to the strap the user chose.
- **HealthKit:** `HKWorkoutBuilder` only. `HKWorkoutSession` and `HKLiveWorkoutBuilder` are iOS 26 APIs on iPhone, so they aren't used.
- **Out of scope for v1:** Zepp/Huami sync, sleep, HRV and recovery, GPS, Apple Watch, cloud sync, nutrition, program builders, plate math, RPE, notifications, widgets. The GitHub repo description mentions sleep; that's a later idea, not v1.

## Build and test

```sh
swift test                 # core tests; macOS or Linux, no Xcode needed
scripts/test-ios.sh        # everything else; needs Xcode 26.6+ and an iOS simulator
python3 scripts/generate-project.py   # after adding, removing or renaming any source file
```

The project is generated and committed. CI fails if `Vitals.xcodeproj` differs from the generator's output. So never hand-edit the project: change the generator, regenerate, and commit both. The generator picks up `Vitals/**/*.swift`, `VitalsTests/*.swift`, `VitalsUITests/*.swift` and `Vitals/Resources/*` by itself. A new test file that uses SwiftData or the app target must also go in `Package.swift`'s `exclude` list, or `swift test` breaks.

Swift 6 language mode, strict concurrency, and warnings treated as errors are on for every target.

## CI

`ios.yml` runs two jobs on `macos-26` with Xcode 26.6:
- **core:** `swift test`.
- **ios:** the generator check, then `scripts/test-ios.sh` on an iPhone 17 Pro simulator (iOS 26.5).

Things to know:
- **Pushes:** run CI unless only `**.md` or `docs/**` changed.
- **Pull requests:** jobs run only for forks. For same-repo PRs they show as "skipped", because the push run already covers the commit.
- **Manual runs** (`workflow_dispatch`): the `screenshot_previews` input prints small JPEG previews of the UI test screenshots in the log. Manual runs use their own concurrency group, so they don't cancel push runs.
- **Artifacts:** each run uploads `screenshots` and `test-results`.

**Reading screenshots from a cloud sandbox.** Artifact downloads from blob storage are blocked by the sandbox proxy, so use the log instead:
1. Dispatch `ios.yml` on your branch with `screenshot_previews: true`.
2. When it finishes, fetch the `ios` job's log with a large tail (about 5000 lines). The tool saves big results to a file.
3. Run `python3 scripts/extract-screenshot-previews.py <saved log> <dir>`.
4. Open the JPEGs. You get `1-train` through `8-exercise-history`.

Logs aren't available until a job has finished.

## Lessons learned (don't relearn these)

- **SwiftData:** a `ModelContext` doesn't keep its `ModelContainer` alive. `WorkoutStore` holds the container; dropping it crashes every store call. Link relationships after `context.insert`, never in model initializers.
- **CoreBluetooth with Swift 6:** the central manager uses `queue: nil`, so callbacks arrive on main. Delegate methods are `nonisolated` and hop with `MainActor.assumeIsolated`. CoreBluetooth objects cross that boundary in `MainQueueValue`, an `@unchecked Sendable` box.
- **Bluetooth reconnection** uses a pending `connect`, which never times out. Bluetooth power-off invalidates peripherals, so they're fetched again on power-on.
- **The bottom bar must stay stacked under the pages** in a `VStack`. As a `.safeAreaInset` it was ignored by the tabs' `NavigationStack`s, which drew the rest clock and the end of every page under the bar. The UI test now asserts the rest clock sits above the bar.
- **UI test screenshots are best effort.** The CI simulator once timed out taking one while the app was idle (run 7). A failed capture is recorded as an expected failure, and every real assertion still stops the test.
- **xcresulttool:** `export attachments` writes a `manifest.json` with no trailing newline, so the first preview marker shares its line.
- **Records are recomputed from the persisted log every time.** When writing tests, check the Epley math: 110 × 3 (121) beats a 100 × 5 baseline (116.7) on both heaviest load and estimated 1RM.
- **HealthKit on iOS 17:** `finishWorkout()` can succeed but return no workout while the phone is locked. Samples added before a failure aren't removed; their sync identifiers keep retries from duplicating them.
- **Permission prompts:** Bluetooth starts at launch only if a strap was chosen before, so people without a strap never see a Bluetooth prompt.
